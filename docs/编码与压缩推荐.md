# 编码与压缩推荐表（已对齐 Cloudflare Pages + Cloudinary 免费版限制）

> 编码数字来自实测：同一条 72 秒 / 673.4 MB / 3200×1800 / 120fps 的航拍原片，
> 在 20 核 Windows 机器上用 ffmpeg 跑出来。
> 平台限制来自官方文档（2026-11 核实），站点规模来自本项目线上站实测。
> **先看第 1 节的硬限制，再挑编码档位——顺序反了就会白压一遍。**

---

## 1. 两个平台的硬限制（决定一切的前提）

### Cloudflare Pages（放网页、照片、小视频）

| 限制 | 数值 | 影响 |
|---|---|---|
| **单文件** | **25 MiB**（免费/付费都一样） | 超过就传不上去，这是第一道线 |
| 每站点文件数 | 免费 20,000 / 付费 100,000 | 照片+视频+封面都算 |
| **拖拽上传文件数** | **1,000**（Wrangler 才是 20,000） | 素材稍多就必须用 Wrangler，不能用网页拖拽 |
| 构建次数 | 免费 500 次/月，单次超时 20 分钟 | 别反复 push 触发构建 |
| 静态流量 | 不限量 | **视频放这里最划算** |
| 总容量 | 官方无总 GB 条款 | 理论上限 20,000 × 25 MiB ≈ 488 GB |
| 时效 | 官方无过期条款 | 不主动删就长期在线 |

来源：<https://developers.cloudflare.com/pages/platform/limits>、
<https://developers.cloudflare.com/pages/platform/direct-upload/>

### Cloudinary（只放 Pages 装不下的大视频）

| 限制 | 数值 | 影响 |
|---|---|---|
| **单视频** | **100 MB**（免费版） | 超过必须切段，分块上传也不能突破 |
| **单图片** | **10 MB**（免费版） | 本项目照片最大 513 KB，余量 20 倍 |
| **每月额度** | **25 credits** | **1 credit = 1 GB 存储 或 1 GB 流量 或 1000 次变换，三者共用一个池** |
| 超额行为 | **不是扣费，是警告后停号** | 视频站最容易踩：流量一冲就全站视频失效 |

来源：<https://cloudinary.com/pricing>、Cloudinary 官方帮助文档（免费版图片 10 MB / 视频 100 MB）

> ⚠️ 网上很多教程写"免费 25 GB 存储 + 25 GB 流量"，那是**旧计费模型**。
> 现在是 25 credits 共用池：存储 2 GB + 流量 23 GB 就已经用满，不是各有 25 GB。

### 由此得出的唯一正确分流

```
成品 ≤ 24 MB   → 直接放 Pages（流量不限量，首选）
24 MB < 成品 ≤ 100 MB → 上传 Cloudinary，用 Pages Functions 代理
成品 > 100 MB  → 两边都放不下，必须切段或降档重压
```

`tools/build_site.py` 的 `videos.max_mb` 默认 **24**（Pages 25 MiB 留 1 MiB 余量），
超过会提示走 Cloudinary；超过 100 MB 会额外警告"必须切段"。
**不要把 max_mb 改成 60 或 100**——那是 Cloudinary 的上限，不是 Pages 的。

## 2. 实测基准：同一条片子的 6 种压法

| # | 设置 | 成品 | 压缩比 | 速度 | 能直接进 Pages？ |
|---|---|---|---|---|---|
| 原片 | H.264 3200×1800 / 120fps / 78 Mbps | 673.4 MB | — | — | ✗ 远超 25 MiB |
| A | 1080p / H.264 / CRF 24 / medium | 22.9 MB | 3.41% | 1.79× 实时 | ✓ 刚好卡线，余量小 |
| B | **1080p / H.264 / CRF 26 / medium**（默认） | 17.7 MB | 2.63% | 1.90× 实时 | ✓ **推荐** |
| C | 1080p / H.264 / CRF 28 / fast | 12.5 MB | 1.86% | 1.95× 实时 | ✓ 余量充足 |
| D | 1080p / HEVC / hevc_qsv / Q 25（硬件） | 16.5 MB | 2.45% | **3.1× 实时** | ✓ 但旧设备可能播不了 |
| E | 720p / H.264 / CRF 35 / fast | 3.6 MB | 0.54% | 3.1× 实时 | ✓ 体积最小，近景细节丢 |
| F | 1080p / AV1（libaom）/ CRF 40 | 12.2 MB | 1.81% | **0.24× 实时** | ✓ 体积达标但兼容性差 |

三个关键结论：

1. **先降帧率再压，能省一半**：120fps 原片先 `fps=60`，同画质码率需求直接减半。
   线上那份 6.4 MB 的老版本，同参数现在复现只要 3.6 MB，差别就在有没有先降帧率。
2. **硬件编码是提速首选**：3.1× vs 1.9× 实时，画质与 CRF 26 相当。但 HEVC 在旧 iPhone /
   部分微信内置浏览器上可能播不了，**公开相册站建议仍以 H.264 为主**。
3. **换 preset 提速很有限**：medium → fast 只从 1.79× 到 1.95×，大头是 4K 解码+缩放。
   真正提速只有三条路：降分辨率、降帧率、上硬件编码。

## 3. 按原片总量选档（视频）

**所有档位的目标都是"成品 ≤24 MB，直接进 Pages"**，这样完全不消耗 Cloudinary 额度。

| 原片总量 | 推荐设置 | 预计耗时 | 成品预估 | 平台合规 |
|---|---|---|---|---|
| ≤ 300 MB | 1080p / CRF 24 / medium | 1.8× 实时 | 1–3% | 单段基本 ≤24 MB ✓ |
| **300 MB – 1 GB** | **1080p / CRF 26 / medium** | 1.9× 实时 | 2–3% | ✓ 成品 20–40 MB，长段需检查 |
| 1 – 3 GB | 同上 + 先统一 `fps=60` | 1.9× 实时 | 2–3% | ✓ 降帧率后长段也能进 Pages |
| **3 – 10 GB（5 GB 属这档）** | 精华段 1080p CRF 24；其余 1080p CRF 28 fast；长航拍 720p CRF 30 | 2–3× 实时 | 1.5–3% | ✓ 分档就是为了都压进 24 MB |
| > 10 GB | 先筛素材，再 1080p CRF 28 + 720p 兜底 | 2–3× 实时 | 2–3% | ✓ 同时注意 20,000 文件上限 |

### 5 GB 素材：怎么又清晰又快

```
第 1 步  统一帧率 fps=60（120fps 原片必做，省一半码率）
第 2 步  批量转 1080p / libx264 / crf 28 / preset fast
         （有 Intel 核显可试 hevc_qsv Q25，但要确认目标手机能播 HEVC）
第 3 步  挑 5–10 段精华重压：1080p / crf 24 / medium
第 4 步  逐段查体积：>24 MB 的降到 720p 或 crf 30 重压；>100 MB 的切段
```

预计：**约 4–10 分钟跑完**（按本项目航拍素材密度），成品合计 **100–150 MB，全部可直接进 Pages，
Cloudinary 额度消耗 0**。普通手机素材约 20–40 分钟，成品 300 MB – 1 GB。

### 1 GB 素材：怎么快、清晰、占内存少

```
一条命令：-c:v libx264 -crf 26 -preset medium -movflags +faststart
```

- 耗时：**1–2 分钟**
- 成品：**20–40 MB**，直接进 Pages
- 内存：ffmpeg 流式编码，常驻 **1–2 GB**，不随素材总量增长
- 磁盘：不产生中间文件，只需 原片 + 成品 + 10% 余量

## 4. 单段时长上限（25 MiB 换算）

| 档位 | 成品码率 | 24 MiB 能装 | 建议单段 |
|---|---|---|---|
| 1080p / CRF 26 | 2,000–4,000 kbps | **50–101 秒** | ≤60 秒 |
| 1080p / CRF 28 | 1,500–2,500 kbps | 81–134 秒 | ≤90 秒 |
| 720p / CRF 30–35 | 600–1,500 kbps | 2.2–5.6 分钟 | ≤3 分钟 |

公式：`可装秒数 = 201,327 kbit ÷ 成品码率(kbps)`（24 MiB = 201,327 kbit）。

> 注意：这比"按 Cloudinary 100 MB 算"严格得多。
> 想放 3 分钟的 1080p 长镜头，成品约 45–90 MB，**必须走 Cloudinary**，
> 而 Cloudinary 只有 25 credits，所以**优先切段，而不是优先上传**。

原片体积基本不设限（673 MB 原片压出 17.7 MB），**真正要控制的是单段时长**。

## 5. 照片推荐表

流程是"先缩到长边 N，再存 WebP q"，原图多大都无所谓。

| 照片类型 | 设置 | 成品 | Pages 25 MiB | Cloudinary 10 MB |
|---|---|---|---|---|
| 手机直出 12MP | 长边 1600 / q82 | 50–150 KB | ✓ 余量 170 倍 | ✓ 余量 60 倍 |
| 相机 24MP、大光比风景 | 长边 1800 / q86 | 150–400 KB | ✓ | ✓ |
| 全景 / 超宽长图 | 长边 2000–2400 / q84 | 300–600 KB | ✓ | ✓ |
| 截图 / 含文字表格 | **PNG 或 WebP q90** | 100–500 KB | ✓ | ✓ |
| 超过 1000 张 | 长边 1400 / q80 | 30–80 KB | ✓ | ✓ |

本项目 606 张实测：平均 **77 KB**、中位 55 KB、95 分位 222 KB、**最大 513 KB**，
超过 1 MB 的 **0 张**。

**照片一律放 Pages，不要上 Cloudinary**——照片体积小、数量多，
放 Cloudinary 只会白白消耗流量额度。唯一注意点：**含文字的图别用 q82，字会糊**。

## 6. Cloudinary 额度账（为什么视频要尽量留在 Pages）

本项目线上站实测（2026-11-21）：

| 项目 | 实测值 |
|---|---|
| 视频引用总数 | **339 条** |
| 其中走 Pages 本地 `media/` | **303 条**，合计 2.43 GB，最大单段 **24.9 MB** |
| 其中走 Cloudinary 代理 | **36 条** |
| 站点文件总数 | 2,016（>1,000，**必须用 Wrangler 部署，不能网页拖拽**） |
| 照片 | 606 张，最大 513 KB |

假设把所有视频都搬到 Cloudinary（存储 2.43 GB = 2.43 credits），
按每次访问平均看 3 段、平均每段 8.2 MB 估算流量：

| 月访问量 | 流量 | 加上存储后总消耗 | 25 credits 够吗 |
|---|---|---|---|
| 100 | 2.4 GB | 4.8 credits | ✓ 宽裕 |
| 500 | 12.0 GB | 14.5 credits | ✓ 偏紧 |
| **1,000** | **24.0 GB** | **26.5 credits** | **✗ 超额，会被停号** |
| 3,000 | 72.1 GB | 74.5 credits | ✗ 远超 |

**结论：抖上一条视频火了，Cloudinary 免费额度当天就能烧穿，然后全站视频失效。**
所以正确策略是：

1. 视频优先压进 24 MB 放 Pages（静态流量不限量）
2. 只有实在压不下去的长段才上 Cloudinary
3. 上了 Cloudinary 的那些，**要盯着控制台的 credits 用量**
4. 通过 Pages Functions 代理播放时，还会占用 Workers 免费额度
   （10 万请求/天、单请求 10 ms CPU），代理路径不是零成本

## 7. 为什么不用 AV1

| 维度 | H.264 | HEVC | AV1 |
|---|---|---|---|
| 同画质体积 | 1× | ≈0.75× | ≈0.70× |
| 编码速度（实测） | 1.9× 实时 | 3.1× 实时（硬件） | **0.24× 实时** |
| 旧 iPhone / 微信浏览器 | 全支持 | 多数支持 | **大概率打不开** |
| 教学难度 | 低 | 中 | 高 |

AV1 只省 30% 体积，却慢 4–8 倍，而且**体积本来就已经达标**（12.2 MB < 24 MB），
省下来的额度对 Pages 毫无意义（Pages 流量不限量）。**公开相册站不推荐 AV1。**

## 8. 磁盘与内存占用

| 项目 | 数值 | 说明 |
|---|---|---|
| ffmpeg 常驻内存 | 1–2 GB | 流式编码，不随素材总量增长 |
| 中间文件 | 0 | 别用剪辑软件导出"中间无损版"，直接 ffmpeg 一进一出 |
| 成品占用 | 原片的 0.5%–25% | 720p 约 0.5–10%；1080p 约 2–25% |
| 预留空间 | 原片 + 成品 + 10% | 同类素材放同一块盘，避免跨盘拷贝 |

## 9. 五个必须写进流程的保险

1. **24 MB 分流线**：成品 >24 MB 先尝试降档重压，压不下去才上 Cloudinary；>100 MB 必须切段。
2. **变大就回滚**：压完比原文件还大就保留原文件。实测 213 段里有视频压完涨到 367%。
3. **码率下限**：1080p 低于 2,000 kbps、720p 低于 800 kbps 会发软，必须人工看一眼。
4. **120fps 先降到 60fps**：不降直接压，等于白花一倍码率。
5. **部署用 Wrangler**：站点超过 1,000 个文件时，网页拖拽会静默漏文件。

### 部署前自查命令

```powershell
# 有没有超过 Pages 25 MiB 的文件
Get-ChildItem -Recurse -File | Where-Object { $_.Length -gt 25MB } |
  Select-Object Name, @{n='MB';e={[math]::Round($_.Length/1MB,1)}}

# 文件总数是否超过拖拽上限 1000 / 站点上限 20000
(Get-ChildItem -Recurse -File).Count
```

两条都干净，再 `wrangler pages deploy`。
