# 旅行相册网站搭建指南（避坑版）

> 这份文档总结了从素材到上线全过程踩过的所有坑，照着做就能不走弯路。
> 核心技术栈：纯静态站（HTML + CSS + 原生 JS）+ Cloudflare Pages 部署 + Cloudinary 视频 CDN（通过 Pages Functions 反向代理）。

---

## 一、网站部署块（最容易踩坑）

### 1. 为什么不能直接把所有视频扒到 Pages 上？

**坑：Cloudflare Pages 单文件限制 25MB，超大视频直接传不上去。**

正确做法：
- 照片和小视频（< 25MB）直接放 Pages 静态目录
- 大视频（> 25MB）上传到 Cloudinary，通过 Pages Functions 代理访问

### 2. 视频托管方案选型（三个死路，一条活路）

| 方案 | 结果 | 原因 |
|------|------|------|
| Cloudflare R2 | ❌ 死路 | 必须绑银行卡，个人用户不愿绑 |
| Cloudinary 直接 CDN 链接（res.cloudinary.com） | ❌ 死路 | 国内被安全软件拦截，用户打开就是红色警告页 |
| 独立 Workers 域名（xxx.workers.dev） | ❌ 死路 | 国内直接打不开 |
| **Cloudinary + Pages Functions 反向代理** | ✅ 唯一可行 | 用自己的 pages.dev 域名代理 Cloudinary 内容，绕开国内拦截 |

**最终方案原理：**
- 视频文件上传到 Cloudinary 存着
- 网站上引用路径写成 `/media/video/upload/xxx.mp4`
- Pages Functions 拦截 `/media/video/` 开头的请求，转发到 Cloudinary 拉取
- 用户看到的全程是你自己的 pages.dev 域名，国内访问正常

### 3. Pages Functions 代理脚本——路由范围是最容易错的地方

**大坑：一开始把代理脚本放在 `functions/media/[[path]].js`，拦截了所有 `/media/` 路径请求，导致本地静态照片和小视频全部 404。**

正确做法：
- 代理脚本路径：`functions/media/video/[[path]].js`
- 只代理 `/media/video/` 开头的请求（也就是 Cloudinary 托管的大视频）
- 其他 `/media/` 路径（本地照片、本地小视频）直接走静态文件，不受影响

**关键：路由粒度一定要细！只代理需要代理的子路径，不要拦截整个目录。**

### 4. data.js 编码——中文乱码直接全站白屏

**坑：data.js 如果带 BOM 或者编码不对，`window.TRIPS` 根本无法解析，打开就是黑屏。**

正确做法：
- data.js 必须保存为 **UTF-8 无 BOM** 编码
- 用 VS Code 或记事本改完后确认右下角编码是 "UTF-8" 不是 "UTF-8 with BOM"
- PowerShell 写文件时用 `[IO.File]::WriteAllText` 而不是 `Out-File`（后者会自动加 BOM）

### 5. PowerShell 操作文件名带方括号的文件——必须用 -LiteralPath

**坑：`functions/media/video/[[path]].js` 这种文件名里有 `[` `]`，PowerShell 会把它们当通配符，导致复制/删除操作静默失败，文件没动你还以为改成功了。**

正确做法：所有涉及 `[[path]]` 这类文件名的命令，全部加 `-LiteralPath` 参数：
```powershell
Copy-Item -LiteralPath "源路径\[[path]].js" -Destination "目标路径"
```

### 6. 部署命令模板

```powershell
$env:CLOUDFLARE_EMAIL = "你的邮箱"
$env:CLOUDFLARE_API_KEY = "你的Global API Key"
$env:CLOUDFLARE_ACCOUNT_ID = "你的Account ID"

cd 到 deploy 目录
wrangler pages deploy . --project-name 你的项目名
```

## 二、画质块（视频/图片处理）

### 1. 视频压缩参数——差一档就是糊和不糊的区别

**坑：一开始为了压到 25MB 以内，用了 crf35 + 720p，用户反馈"太糊、有马赛克"。**

正确参数（1080p 清晰档）：
```
-crf 28 -preset slow -c:a aac -b:a 128k
```

参数说明：
- **crf 28**：清晰度和体积的最佳平衡点，肉眼看和原片差别极小
- **crf 35 及以上**：开始出马赛克、细节糊，手机上看尤其明显
- **分辨率**：保持 1080p，不要降 720p
- **音频**：AAC 128k 足够

> 仓库里的 `tools/build_site.py` 默认用的是 **crf 26**（比 28 更清晰一点，体积略大）。23–28 都是可接受区间，低于 23 体积会明显变大，高于 28 就开始糊。用户对画质敏感时，往小调。

### 2. 上传 Cloudinary 的大小上限

**坑：73MB 的视频上传失败，51MB 左右成功。**

正确认知：
- Cloudinary 免费套餐单文件上传上限约 50-60MB
- 超过这个大小的视频，再压小一点再传（crf 28 再压一点，或者稍微降帧率）
- 不要直接把原始视频传上去，一定先压一遍

### 3. ffmpeg 路径——本机有两个，别用错

**坑：剪映自带的 ffmpeg 只有硬件编码器（h264_nvenc），压缩出来体积大、画质差；Recordly 自带的 ffmpeg-static 才有 libx264 软件编码器，压缩质量好。**

正确路径：
```
C:\Users\<你的用户名>\AppData\Local\Programs\Recordly\resources\app.asar.unpacked\node_modules\ffmpeg-static\ffmpeg.exe
```

**判断方法：如果 ffmpeg 命令里 `-c:v libx264` 报错说找不到编码器，就是用错了 ffmpeg。**

### 4. 重复视频排查方法

**坑：手动翻根本看不出哪些是重复的，要靠数据比对。**

正确流程：
1. 先用 ffprobe 提取所有视频的时长
2. 按时长分组，时长完全相同的才可能是重复
3. 再对比这组里的封面图（用 PIL 算 MSE 均方误差）
4. **两个条件都满足才算重复**：时长一样 + 封面几乎一样（MSE < 500）
5. 只删一个，保留另一个（用户指定保留的那个除外）

### 5. 视频加载慢 / 加载不出来——90% 是代理路径配错了

**典型现象：**
- 用户反馈"点进去大部分视频都是黑的，偶尔刷新出一两个"
- "所有视频都比之前加载慢了很多"
- 手机上看界面全黑，等半天只出来一两个视频

**根因（最容易犯的错）：**
Pages Functions 代理脚本放错了层级，把**所有 `/media/` 路径都拦截了**，包括本地应该直接走静态托管的照片和小视频。

流程变成了：
```
用户请求本地视频 → Pages Functions 拦截 → 转发到 Cloudinary → Cloudinary 上没有这个文件 → 卡住/超时
```

而不是正确的：
```
用户请求本地视频 → 直接走 Pages 静态文件 → 秒开
用户请求 Cloudinary 大视频 → Pages Functions 拦截 → 转发到 Cloudinary → 拉取成功
```

**正确做法：**
- 代理脚本必须放在 `functions/media/video/[[path]].js`
- 只代理 `/media/video/` 开头的请求（也就是 Cloudinary 上的大视频）
- 其他 `/media/` 路径（本地照片、本地小视频）直接走静态文件，不经过 Functions

**排查步骤（遇到加载问题先做这个）：**
1. 打开浏览器 F12 → Network 标签
2. 刷新页面，看视频请求的状态：
   - **一直 pending / 转圈**：代理脚本把本地文件也转发了，那边没有就卡住 → 检查路由层级
   - **404 Not Found**：要么文件真的不存在，要么路径拼错了
   - **200 但加载很慢**：代理本身是通的，是 Cloudinary 源站在国外导致的正常延迟
3. 对比：如果新部署的版本比之前所有视频都慢，基本就是代理范围配大了

## 三、交付 checklist（给别人做之前对照一遍）

### 网站部署
- [ ] Pages Functions 代理脚本放在 `functions/media/video/[[path]].js`，**只代理 `/media/video/` 子路径**，不要拦截整个 `/media/` 目录
- [ ] 本地小视频和照片直接走静态文件，不经过 Functions 代理
- [ ] data.js 是 UTF-8 无 BOM 编码
- [ ] 所有带 `[[` `]]` 文件名的操作都用了 `-LiteralPath`
- [ ] 部署前打开 F12 → Network 验证：本地视频请求是 200 直接返回，Cloudinary 视频请求经过代理

### 画质
- [ ] 视频压缩用的是 crf 23–28 区间 + 1080p，不是 crf35 + 720p
- [ ] 上传 Cloudinary 的视频单文件 < 60MB
- [ ] 用的是有 libx264 软件编码器的 ffmpeg（不是只有硬件编码器的那个）
- [ ] 重复视频已经按时长 + 封面 MSE 双条件排查过

### 互动功能（点赞 / 留言）
- [ ] `wrangler kv namespace create "ALBUM_KV"` 已执行，id 已填进 `wrangler.toml`
- [ ] 点赞接口 POST 一次，数字真的 +1（不是只在前端变化）
- [ ] 留言发一条，刷新页面还在（说明写进 KV 了）
- [ ] 留言内容做了 HTML 转义，输入 `<script>` 不会被具体执行

## 四、给别人发视频时，你需要说清楚的事

如果别人拿素材让你做，你只需要告诉他：
1. **素材规格**：视频原始文件、照片原图，按日期/景点分好文件夹
2. **输出要求**：就是你现在这个网站的效果（暗黑拼贴风格 + 大小错落布局）
3. **不用他操心的部分**：视频压缩、CDN 托管、部署、域名这些你全包

他只需要把素材交给你，剩下的按这份文档走就行。

## 五、点赞和留言（想做互动功能时看这段）

纯静态站自己没有地方存数据，点赞数和留言必须落到一个存储上。Cloudflare 的 **KV + Pages Functions** 是最省事的：不用服务器、不用数据库、不用绑银行卡，免费额度对个人站点完全够用。

### 1. 建 KV 命名空间

```bash
wrangler kv namespace create "ALBUM_KV"
```

它会返回一个 id，把这个 id 填进 `wrangler.toml` 的 `bindings` 里。**不填的话接口会直接 500，但页面看起来完全正常**——这是最容易误判"功能做好了"的地方。

### 2. 两个接口

| 路径 | 方法 | 作用 |
|---|---|---|
| `/api/like` | GET | 读当前点赞数 |
| `/api/like` | POST | 点赞数 +1 |
| `/api/messages` | GET | 取最近 50 条留言 |
| `/api/messages` | POST | 新增一条留言 |

文件放在 `functions/api/like.js` 和 `functions/api/messages.js`，Pages 会自动按路径映射，不需要额外配置。

### 3. 三个坑

**坑一：光靠前端防刷没用。**
点赞的"已点过"标记存在 `localStorage`，用户清缓存就能再点。要严格控制得按 IP 或账号做限流，但个人相册站不值得，接受数字略有水分就行。

**坑二：留言必须转义，否则是 XSS。**
别人输入 `<script>...</script>`，如果你直接 `innerHTML` 塞进去，脚本会在每个访客的浏览器里执行。写入时用 `textContent` 或做 HTML 转义，不要图省事。

**坑三：KV 是最终一致的，别拿它当计数器。**
读 counts 再写回，高并发下会丢数。相册站一天几十个赞，冲突概率极低，可以接受；真要精确得用 Durable Objects。

### 4. 验证方法（做完一定要手测）

```bash
curl https://你的域名/api/like          # 应该返回 {"count":N}
curl -X POST https://你的域名/api/like   # 再调用一次，count 应该 +1
curl https://你的域名/api/messages       # 应该返回 {"messages":[...]}
```

数字真的变了、刷新后还在，才算做成了。只看页面按钮有反馈，不算。
